# 05. 과제 생성 규칙

> 최종 수정일: 2026-11-24

과제 내용을 정하는 **정책**입니다. 프레임워크별 구체 값은 [06](06_frameworks.md), 화면 유형별 구성은 [07](07_layouts.md)에 있습니다. 정책을 바꾸면 [09_decisions](09_decisions.md)에 기록합니다.

## 난이도 정의

| 구분 | 초급 (basic) | 중급 (intermediate) |
|---|---|---|
| 목적 | 컨트롤 사용법과 이벤트·바인딩 연습 | 실무 레이아웃 패턴과 CRUD 흐름 연습 |
| CRUD | 없음 (화면 안에서만 동작) | 조회·등록·수정·삭제 모두 |
| DB | 사용 안 함 | 사용 (직접 설계) |
| 코드 구조 | 화면 / 로직 분리 | 3-tier |
| 화면 유형 | 초급 6종 ([07](07_layouts.md)) | 중급 6종 ([07](07_layouts.md)) |
| 요구사항 카드 | 4개, 기능 이름으로 구분 (입력·계산 등) | 4개, R·C·U·D |
| 구현 힌트 | 있음 | 없음 |
| 데이터 설계 가이드 | 없음 | 있음 |

## 필수/선택 기능 원칙

**필수 기능만으로 과제를 통과할 수 있어야 합니다.** 편의 기능은 모두 선택(가산점)입니다.

선택 기능으로 분류하는 것:
- 드래그 앤 드롭 (카드 이동, 순서 변경, 파일 끌어 놓기, 블록 시간 변경)
- 차트·그래프, 증감률 같은 부가 통계
- 엑셀·파일 내보내기, 클립보드 복사, 인쇄
- 정렬·페이징, 스플리터, 우클릭 메뉴, 더블클릭 단축 동작
- 행 색상 강조, 현재 시각 표시선, 검색어 강조 같은 시각 효과
- 인증·권한, 낙관적 업데이트, URL 상태 동기화, 문서 자동 생성

선택 기능이 화면의 핵심 동작이라면 **버튼 기반 대안을 필수로** 둡니다.
- 칸반 드래그 → [다음 단계로 이동] 버튼
- 우클릭 메뉴 → [대여 처리]·[반납 처리] 버튼
- 빈 칸 더블클릭 등록 → [새 예약] 버튼

예시 화면에서 선택 기능 영역에는 "선택" 배지를 붙입니다.

## 코드 구조 원칙

| 난이도 | 구조 | 원칙 |
|---|---|---|
| 초급 | 화면 / 로직 2계층 | 화면 코드는 입력을 읽고 결과만 표시, 계산·검증은 별도 클래스(화면 없이 테스트 가능) |
| 중급 | Presentation / Business / Data | 화면 계층에 SQL·DB 접근 금지, 업무 규칙은 Business, Data는 저장·조회만, 의존은 위→아래 한 방향, 계층 간 모델/DTO 전달 |

- **WPF는 초급 포함 MVVM 필수**입니다. 코드 비하인드(.xaml.cs)에는 `InitializeComponent()` 외의 로직을 두지 않습니다. 초급 WPF는 View / ViewModel / Logic 3단으로 구성합니다.
- 프레임워크별 폴더·파일 템플릿은 [06](06_frameworks.md)에 있습니다.
- 중급 아키텍처 규칙 중 하나는 해당 과제의 실제 업무 규칙을 예로 듭니다. (예: "같은 자산명 중복 등록 경고는 Business 계층에 구현")

## 데이터 설계 가이드 (중급)

테이블·API 명세는 **주지 않습니다.** 대신 아래 질문을 과제에 맞게 채워 제공합니다.

1. 화면 항목(…)을 출발점으로, 필요한 테이블과 컬럼을 정해 보기
2. 업무 코드(예: …)와 내부 기본키를 따로 둘지 정하고 이유 적기
3. 상태값을 코드 테이블로 둘지, CHECK 제약으로 둘지 비교하기
4. 등록일시·수정일시·작성자 같은 공통 컬럼 넣기
5. 과제별 관계 고민 포인트 1개 (예: 1:N, 자기 참조, 이력 테이블)
6. (React·NodeJS만) API를 URL·메서드·요청/응답 예시·상태 코드 표로 먼저 정리하기

제출물: README에 ERD와 "왜 이렇게 설계했는지" 3줄 이상

## 예외 처리 작성 원칙

- 과제 고유 조건 2~3개 + 프레임워크 공통 조건 1~2개 ([06](06_frameworks.md))
- "무엇을 입력하면 어떻게 되어야 하는지"가 드러나게 씁니다 (예: "구매일이 오늘보다 뒤면 오류")

## 예상 소요 기간

신입이 해당 언어를 처음 쓰는 경우, **필수 기능만** 기준입니다.

| 화면 유형 | 기본 기간 |
|---|---|
| form, calc, lookup | 1일 |
| todo, settings | 1~2일 |
| wizard | 2일 |
| gridForm, masterDetail, kanban, dashboard, treeGrid | 4~5일 |
| calendar | 5~6일 |

보정:
- WPF 초급 **+1일** (MVVM 기반 클래스를 처음 만드는 시간)
- Python 중급 **−1일** (설정이 적음)

## 권장 일정

실무 투입 전 **약 2주**

| 주차 | 과제 |
|---|---|
| 1주차 | 초급 2개 (서로 다른 화면 유형, 예: form + wizard) |
| 2주차 | 중급 1개 (처음엔 gridForm 또는 masterDetail) + 리뷰·수정 1~2일 |
| (선택) 3주차 | 중급 1개 추가 (kanban, calendar 등) |

## 아이디어 제안 규칙

- 같은 프레임워크·난이도 안에서 **이미 제안한 아이디어는 반복하지 않음**
- **직전 아이디어와 같은 화면 유형을 연속으로 내지 않음**
- 넘긴 아이디어와 같은 업무 분야는 피함
- 프레임워크별 첫 제안 화면 유형은 [06](06_frameworks.md)의 "첫 제안" 값을 따름
- (Mock 모드) 샘플을 다 보면 안내 문구를 띄우고 순서를 섞어 다시 제안
