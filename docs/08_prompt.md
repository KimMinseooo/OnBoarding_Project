# 08. Claude API 프롬프트 설계

> 최종 수정일: 2026-11-24
> 코드 위치: `apps/server/src/prompts`, `apps/server/src/services`

## 역할 나누기: Claude가 만드는 것 vs 서버가 채우는 것

규칙이 정해진 값은 Claude에게 맡기지 않고 서버가 카탈로그([05](05_assignment-rules.md)·[06](06_frameworks.md)·[07](07_layouts.md))로 채웁니다. 그래야 정책을 바꿀 때 프롬프트를 고칠 필요가 없고, 결과가 항상 규칙을 지킵니다.

| 필드 ([04](04_assignment-schema.md)) | 만드는 쪽 | 비고 |
|---|---|---|
| `layout` | Claude | 서버가 준 후보 목록 안에서 선택 |
| `title`, `team`, `scenario`(업무 문제 부분) | Claude | |
| 업무 엔터티 이름 (`Entity`, `slug`, 초급 `Logic` 클래스명) | Claude | 폴더 템플릿에 넣는 값 |
| `requirements`의 업무 항목 | Claude | 서버가 프레임워크 구현 포인트를 뒤에 붙임 (중급) |
| `optionalFeatures`의 업무 항목 | Claude | 서버가 프레임워크 선택 기능을 뒤에 붙임 (중급) |
| `exceptions`의 업무 항목 | Claude | 서버가 프레임워크 공통 조건을 붙임 |
| `dataGuide`의 관계 고민 포인트 1개 | Claude | 나머지 질문은 서버 템플릿 ([05](05_assignment-rules.md#데이터-설계-가이드-중급)) |
| `mockup.data` | Claude | [04](04_assignment-schema.md#mockup) 형식 |
| `learningGoal` | Claude(초급) / 서버(중급, 07의 값) | |
| `scenario`의 구현 방식 문장 | 서버 | [06](06_frameworks.md) |
| `controls`, `tech`, `hints` | 서버 | [06](06_frameworks.md)·[07](07_layouts.md) |
| `architecture` | 서버 | 06 폴더 템플릿 + 엔터티 이름 |
| `rubric` | 서버 | [05](05_assignment-rules.md#채점표) 배점 + 요구사항·예외 문구 |
| `estimatedDays`, `id` | 서버 | |

## 요청 흐름

1. 웹 → `POST /api/assignments { framework, level, recent }`
2. 서버가 **후보 화면 유형** 계산: 해당 난이도의 유형 중 `recent[0].layout`과 다른 것
3. 프롬프트 조립 → Claude 호출 (구조화 출력: tool use, 입력 스키마 = Draft 스키마)
4. Draft 검증(zod) → 실패하면 오류 내용을 붙여 **1회 재시도** → 또 실패하면 502
5. 서버가 나머지 필드를 채워 `Assignment` 완성 → 최종 스키마·추가 검증([04](04_assignment-schema.md#검증-규칙-스키마-외-추가-검사)) → 응답

## 프롬프트 구성

**시스템 프롬프트 (고정 부분, 프롬프트 캐싱 대상)**

```
너는 IT 회사의 15년 차 풀스택 개발자이자 신입 교육 담당자다.
신입사원이 실무 투입 전에 2주 동안 수행할 과제의 "업무 내용"을 만든다.

원칙:
- 실제 회사에서 흔히 있는 사내 업무 문제를 고른다. (총무·인사·재무·구매·고객지원·생산 등)
- 필수 요구사항은 편의 기능 없이도 완성 가능한 핵심 동작만 쓴다.
- 편의 기능(드래그 앤 드롭, 차트, 내보내기, 정렬·페이징, 우클릭 메뉴, 시각 강조 등)은 optionalFeatures에만 넣는다.
- 예외 조건은 "어떤 입력이면 어떻게 되는지"가 드러나게 쓴다.
- 인물·회사 이름은 실존하지 않는 예시로 쓴다.
- 모든 문장은 한국어, 명세서 말투(~한다/명사형)로 짧게 쓴다.
- 결과는 반드시 create_assignment_draft 도구로만 반환한다.
```

**사용자 메시지 (요청마다 바뀌는 부분)**

```
프레임워크: {framework 표시 이름}
난이도: {초급|중급} — {05의 난이도 정의 한 줄}
선택 가능한 화면 유형:
{후보 유형마다: id, 이름, 구성, 필수 동작 — 07에서 자동 삽입}

최근 제안(겹치지 말 것):
{recent의 title, layout 목록}

요구사항 카드 형식: {초급: 기능 이름 4개 | 중급: R·C·U·D 4개}
mockup.data 형식: {선택한 유형의 04 형식 — 도구 스키마로 전달}
```

- 07·05·06의 내용은 **카탈로그 코드에서 읽어 삽입**합니다. 문서 문장을 프롬프트 파일에 복사하지 않습니다.
- 모델은 환경 변수 `ANTHROPIC_MODEL`로 지정합니다.

## 출력 검증 실패 시 재시도 메시지

```
이전 결과가 다음 규칙을 어겼다. 같은 아이디어로 고쳐서 다시 반환하라.
- {zod 오류 경로와 메시지 목록}
```

## 생성 품질 점검표

로드맵 7단계에서 생성물을 검토할 때 씁니다.

- [ ] 실제 회사에 있을 법한 업무인가
- [ ] 필수 요구사항만으로 화면이 완성되는가 (선택 기능이 필수에 섞이지 않았는가)
- [ ] 요구사항·예외 문장이 구현 가능한 수준으로 구체적인가
- [ ] 예시 화면 데이터가 업무와 맞고, 행·열 개수와 상태 값이 일관적인가
- [ ] 최근 제안과 업무·화면 유형이 겹치지 않는가
- [ ] 예상 기간 안에 신입이 끝낼 수 있는 분량인가 ([05](05_assignment-rules.md#예상-소요-기간))
- [ ] 실존 인물·회사 이름이 없는가

반복되는 문제는 시스템 프롬프트의 원칙이나 추가 검증 규칙으로 옮기고 [09](09_decisions.md)에 기록합니다.
